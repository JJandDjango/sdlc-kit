name: sdlc-flow-g1
description: The G1 flow of /sdlc - the G1 venue - lint and model recorded, the 11 review items asked of a person, the review signed on that person's word, the verdict read.
---

<purpose>
The G1 flow of the `/sdlc` skill, the G1 venue: `/sdlc g1 {id}` runs
after intake and before a unit's first task. It records G1.1 and G1.2,
leads a person through G1.3's 11 items, and reads the verdict. The
flow writes no file itself: `g1-record` is the one writer, and it
writes a review only on a named person's word. The review asks none of
ready checks 1 to 15 again: the interview and intake ask them, as
today. Dispatched by {skill-dir}/SKILL.md on `/sdlc g1`; its
constraints and criteria bind here. {skill-dir} is the directory
holding SKILL.md. {id} is the feature's id, the second argument.
</purpose>

<instructions>
R1. READ the contract at `specs/{id}/contract.yaml`. This step finds out whether the review may start; it records nothing. RUN `python -m taskcontract validate specs/{id}/contract.yaml --profile ready`, one Bash call. Exit 0 means the contract is ready-green. On any other exit the contract is not ready-green: STOP, REPORT the command's lines, run nothing more, and return to the conversation; intake makes a contract ready-green. Then RUN `python -m taskcontract g1-check {id}`, one Bash call, to learn whether G1 is active for the feature. Exit 0 or exit 1 means G1 is active: either is a result, and the flow goes on to R2. Exit 2 with the line `{id}: G1 is not active` means the feature needs no G1: STOP, REPORT that line, run nothing more, and return to the conversation. Any other exit 2 is a call the kit cannot use: STOP in the same way with its line.

R2. READ the two declarations: the `g1:` key of `.sdlc/config.yaml`, which names the boundary schemas, and `specs/components.yaml`, which names the components. A declaration is absent when its file is absent, or when the first file holds no `schemas:` list under `g1:`. When a declaration is absent, SHOW its form, as below, and STOP: REPORT which one is absent, run nothing more, and return to the conversation. The flow writes neither file and proposes no value for one: a person writes a declaration, never the flow. After the person has written it, the flow runs again from R1.
    The form of `.sdlc/config.yaml`:
        g1:
          exempt: []
          schemas:
            - paths: [api/*.yaml]
              linter: spectral
              pin: .spectral.yaml
    The form of `specs/components.yaml`:
        version: 1
        components:
          - id: ledger
            paths: [src/ledger/]
            hard_core: true
            oracle: concurrency
            model: specs/models/ledger.tla
            model_config: specs/models/ledger.cfg
            checker: tlc
    `schemas: []` and `components: []` each say none: a list that is written and empty is a declaration, and the flow goes on.

R3. RUN `python -m taskcontract g1-record lint {id}`, one Bash call. It lints each boundary schema in scope and records G1.1. SHOW its lines. Exit 0 means the record reads clean, or no schema is in scope. Exit 1 means G1.1 failed, with its message printed: a result, never a failed step, and the flow goes on to R4. Exit 2 means nothing was written: STOP, REPORT its lines, and return to the conversation.

R4. RUN `python -m taskcontract g1-record model {id}`, one Bash call. It checks the model of each hard core in scope and records G1.2. SHOW its lines. Exit 0 means the record reads clean, or no hard core is in scope. Exit 1 means G1.2 failed, with its message printed: a result, and the flow goes on to R5. Exit 2 means nothing was written: STOP, REPORT its lines, and return to the conversation.

R5. ASK the person the 11 items of G1.3's review, one at a time, in the item's own words, as they stand below. The person reads them against the requirements document at `docs/features/{id}.md` and, for a pair, the design document at `docs/features/{id}.design.md`. For each item SHOW its number and its words, then ASK one question: checked or unchecked. Take one answer, the person's own, before the next item is shown.
    1. Testable - a mechanical check could decide it; names observable behavior, not internals.
    2. Unambiguous - one reading; quantities carry units and bounds; error behavior stated, not implied.
    3. Traceable - cites the task-contract unit it satisfies.
    4. Complete over units - every decomposition unit has >=1 criterion.
    5. Covers the sketch - every `acceptance_sketch` item matured into a criterion, or explicitly retired with a reason.
    6. Consistent - no two criteria demand conflicting behavior.
    7. Respects non-goals - nothing specifies excluded scope.
    8. Boundary + error paths - each in-scope input surface has >=1 boundary criterion and >=1 error-path criterion; each external dependency has >=1 system-level failure criterion ("on dependency X unavailable, the system does Y") - S9 extension, the chaos question's routed coverage.
    9. Property-spec applicability - surfaces with algorithmic/invariant behavior carry property or metamorphic specs (pattern 3), or a recorded reason why not.
    10. Schema presence - every in-scope service/trust boundary has a boundary schema (pattern 4).
    11. Oracle designation answered - the component declaration record answers the generated-input oracle question for every component touched: differential-gated (naive reference authored), fuzz-gated (targets declared; mandatory for trust-boundary parsers and native-interop wrappers, no opt-out), property-only, concurrency-gated (tripwire-checked at G5.4), soak-designated, or none-with-justification; trace-gating derives from 0007, never opted. Absence of an oracle is an authored, reviewed decision (S9 rubric).
    For items 3 and 4, SHOW intake's `Ready:` rows, one from each document's revision table, as the evidence. The rows are evidence for the person to read, never an answer. For an item left unchecked, ASK which section of the requirements document or the design document the item concerns, and hold the person's words. A section's name is one line that holds a letter or a digit; ASK again for one that does not. An item with no answer from the person is asked again, never filled in. An answer that is neither checked nor unchecked is no answer. HOLD each answer as given: the flow changes none, and records nothing in this step.

R6. SHOW the revisions the signature names: the revisions in intake's `Ready:` rows, one for each document of a pair. The signature stands over all 11 answers on those revisions. Then ASK the signer's name and seat. A name is one line that holds a letter or a digit. A seat is one of the `intake-seat` term's own values. Then SHOW the 11 answers as held and ASK for the word to sign: the person's own yes to signing those answers under that name and seat. Silence, a question or a change to an answer is no word to sign. An agent may draft a reading of an item; it never answers one and never signs. RUN the writer only after the person has given a name, a seat and the word to sign, in one Bash call:
        python -m taskcontract g1-record review {id} --by "{name}" --seat {seat} --checked {checked} --unchecked {n}="{section}"
    {checked} is the numbers of the checked items as one comma-separated list, such as `1,2,3`. `--unchecked {n}="{section}"` is given once for each unchecked item, with the item's number and the section in quotes, as the person named it. With no item unchecked the flag is absent. With no item checked `--checked` is absent. Each of the 11 numbers stands in the call once. SHOW its lines. Exit 0 means the review is recorded with all 11 items checked. Exit 1 means the review is recorded with an item unchecked, and its message names the item: a result, never a failed step. After either, go on to R7. Exit 2 means nothing was written, as for a seat the term lacks or a document with no `Ready:` row that names a revision: STOP, REPORT its line, and return to the conversation. A person who declines to sign gets no review record: run no writer, and go on to R7.

R7. RUN `python -m taskcontract g1-check {id}`, one Bash call. It reads the records and the declarations and gives the verdict; it runs no tool and writes nothing. SHOW its lines, then name the next step. REPORT ends on one of two lines, verbatim with the feature's id: the first for exit 0, when G1 reads done, and the second for any other exit.
    G1 has passed for {id}. Next step: the first unit's approve-tests.
    G1 has not passed for {id}. Fix each line above, then run /sdlc g1 {id} again.
</instructions>
