<purpose>
The Opening flow of `/sdlc:product-specification-interview`: the five
answers that shape the interview (id, origin, title, seats, materials),
with the state file written from the first answer on so a pause anywhere
resumes at the exact step, and the document written as r1 at the close.
A design run opens on DESIGN READ, the requirements document read
before anything is written, and at every later dispatch on DESIGN
CONFIRM, the design confirmed against a newer requirements revision.
Dispatched by {skill-dir}/SKILL.md when no state file exists for the id,
or at the step `next` names; its constraints and criteria bind here.
{skill-dir} is the directory holding SKILL.md.
</purpose>

<instructions>
Each step O1-O5 ends by writing the state file with its answer and `next` set to the following step. A design run asks O1, O4, O5 and O6, each as its design clause says. It asks no origin and no title: it reads both from the requirements document.

DESIGN READ - A design run with no state file of its own READs the requirements document `docs/features/{id}.md` before it writes anything, and stops with nothing written on each of three. No file at the path: REPORT "No requirements document for {id}. Run the requirements interview first." A `## Proposed solution` heading in the file: REPORT "{path} is a combined document. Split it by hand, then run the design interview." No `Signed: request half` row that signs the newest text revision r{n}: REPORT "The requirements document is unsigned at r{n}. The PO seat signs before the design starts." The newest text revision is the highest `rN` of a row that opens on none of `Ready:`, `Measured:`, `Signed:` or `Parked:`. Else HOLD for O1 that revision, the title line, the origin (a bug fix's document holds the four bug-fix sections) and the new terms of the Terms block, and go to O1. A design run reads, and never writes, the requirements document and the requirements run's state file.

DESIGN CONFIRM - A design run with a state file of its own EXECUTEs this step at every dispatch, at any phase, before the step `next` names. The design names one requirements revision: the `requirements r{n}` of the design table's newest text row that names one; the design's table wins over its state file's `requirements_revision`. READ the requirements document's newest text revision. When it is no newer, go on at `next`. On a newer one SHOW "The design names requirements r{n}; the requirements stand at r{m}.", then the revisions between, the requirements table's text rows above the named revision, each on its own line: that row's Changes Made text as the table holds it, which opens with its own revision number, as in `  r4: A non-goal added: no export to CSV`. ASK the engineer seat whether the design still stands against each, and name each revision between in the question: "Confirm the design against r4 and r5?" One revision between reads "Confirm the design against r4?", and three or more "Confirm the design against r4, r5 and r6?" On yes WRITE into the design document one text row, `r{n}: Confirmed against requirements r{m}`, numbered one past the table's last row, with r{m} the requirements document's newest text revision and `seats.engineer` in Revised By; WRITE the state file with `requirements_revision` moved to r{m} and, under `answers.terms`, a new copy of the requirements document's new terms. A design that carries a `Signed: solution half` row is then asked for its signature again, at once, with no run of the checks between: on the seat's word WRITE, right after that text row, with no row between, `r{n}: Signed: solution half. The engineer seat signs r{m}`, where r{m} is that text row; a seat that declines keeps its older signature, and the interview names the revision it covers. A design with no signature takes the text row alone. On no, WRITE nothing: the design keeps the revision it names, and the run asks again at the next dispatch. Either way the run then goes on at the step `next` names, and the step changes no line of the requirements document. A finished run holds `next: null`: there the run goes on at SKILL.md step 1's `complete` route.

O1. ID - CONFIRM the id from SKILL.md step 0; the document's path is `docs/features/{id}.md`. CHECK it with one Bash call `ls docs/features/{id}.md`; a hit means REPORT "A document already exists at {path}. Name another path." and ASK for another id. WRITE the state file `docs/features/{id}.state.yaml`: `schema: spec-interview-state/2`, `id`, `started` (today), `phase: opening`, `next: O2`, `answers: {}`, `open: []`, `history: [{at: now, event: id confirmed}]`. A design run CHECKs the design document's path instead, with one Bash call `ls docs/features/{id}.design.md`, and a hit gets the same report and the ASK for another id; the DESIGN READ then runs again for the id the seat names, since the read held the first id's requirements document. It WRITEs its own state file `docs/features/{id}.design.state.yaml` with the same keys, and adds `requirements_revision` (the revision the read held), `origin` and `title` as read, under `answers.terms` a copy of the requirements document's new terms, and `next: O4`.

O2. ORIGIN - ASK: "Is this a new feature or a bug fix?" A bug fix takes two more answers, one at a time: the incident reference (ticket or alert id) and the regression scenario in one sentence (the case that failed). Record `origin: feature` or `origin: bug-fix`, with `incident_ref` and `regression` for a bug fix.

O3. TITLE - ASK for the feature's title: the outcome, in a few words. The document's title line reads `# {id} - {title}`; the tree and intake read it. Record `title`.

O4. SEATS - ASK who holds the PO seat. A requirements run asks for no engineer seat. Record `seats: {po}`; the name lands in r1, on the status line and, at intake, in `confirmed_by`. A design run ASKs who holds the engineer seat, and asks for no PO seat. Record `seats: {engineer}`; the name lands in the design document's r1 and on its status line.

O5. MATERIALS - ASK whether there is material to start from: a ticket, a PRD, notes, a prior document, as pasted text or a path. When given, READ it and EXTRACT what maps to the template's sections (statement, description, background, existing behavior touched, success criteria, non-goals, prerequisites, checks, error messages, decisions and open questions, notes, terms). SHOW the extraction section by section and ASK the user to confirm each; record confirmed items under `answers.{section}` with `source: material`, so the section's own step shows the material and asks to confirm instead of asking afresh. A conflict between the material and a spoken answer is asked, never resolved silently: "The material says X; you said Y. Which stands?" A design run EXTRACTs what maps to the design template's sections instead (scope, out of scope, interfaces, sources, constraints, units, order, risks and cost, consult cases, decisions and open questions, links out, notes).

O6. CLOSE - WRITE the document `docs/features/{id}.md` as r1 from {skill-dir}/templates/requirements-document.md.template: fill `{date}` (today), `{po}`, `{id}`, `{title}` and `{repo}` (the repo directory's name); a section confirmed at O5 gets its text, and a section that no step has written and O5 did not confirm reads "(not yet asked)"; no step asks Decisions and open questions and Notes, so each holds the material O5 confirmed, else "(none)"; a derived block not yet written carries no stamp, so the Gherkin block gets the tag `[PO seat · derived]` and the body "(none: the Gherkin step writes one scenario per check)", while the template keeps its stamped tag for the step that writes the block; a feature's document drops each block from `{bug fix only}` to `{end bug fix only}`, marker lines included, so it omits the four bug-fix sections and never leaves them empty; a bug fix's document keeps each block with `incident_ref` and `regression` filled and drops only the two marker lines. WRITE the state file with `phase: request`, `next: Q1`, and `history: + {at: now, event: opening complete, document written as r1}`. REPORT the document path and the state file path in one line and return to SKILL.md step 1. A design run WRITEs the document `docs/features/{id}.design.md` as r1 from {skill-dir}/templates/design-document.md.template instead: fill `{date}`, `{engineer}`, `{id}`, `{title}`, `{repo}` and `{m}`, the state file's `requirements_revision`, so r1 reads `against requirements r{m}` and names the revision the read held; a section confirmed at O5 gets its text, and every other section reads "(not yet asked)", Decisions and open questions and Notes among them, since S10 and S12 ask them; the Record block gets the tag `[Intake · derived]` and the body "(none: intake writes the record)", while the template keeps its stamped tag for the step that writes the block. It WRITEs the state file with `phase: solution`, `next: S1` and the same `history` line, REPORTs both paths and returns to SKILL.md step 1.
</instructions>
