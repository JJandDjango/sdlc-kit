Project  SDLC kit: gates that stop agent-written code from degrading a codebase.
Area     The execution node: the team that runs each task of a unit, in any consumer repository.
Feature  execution-team (Standard Development Workflow): the team ships in the plugin, runs the test command a repository declares, and ends a run in a draft PR.
Unit     `e1-declaration` (the first of six, in build order; the contract merged in PR #142 at `24b3d2b`). Session 124.

1. The deliverable. By this session's end `e1-declaration` is built on the branch `session-124-e1-declaration`, graded PASS by Two-Key, and its PR is open for the user's review. Done means, from the contract: "A repository declares `test:` and `wall:`, the kit declares its own, and a task with no `test.command` prints SC2.3's message."
2. Where this sits. The design (`docs/features/execution-team.design.md`, Interfaces 3 and 10) puts the declaration in `.sdlc/config.yaml`: a `test:` block (`command`, `file`, `build`, each an argv list) and a `wall:` block (`functional`, `unit`, `code`, `interface`). `taskcontract` reads the test command; `workflows/tools/task.py start` is the one place a task starts, and with no `test.command` it prints SC2.3's message, `Task {task} did not start: the repository declares no test command.`, writes nothing and exits 1. e1 builds `start`; `fail`, `stop`, `end` and the rounds file are e5's (SC4.1 to SC4.3), the hook that reads `wall:` is e3's, and the scripts that run the command are e2's. The usage page is written here with every marker red (the design's Units note), and e1 turns its own markers green. G1 reads `g1-green: execution-team`, so `progress start` is not refused.

6. Rulings needed: none. Readings, each ruled from the documents' purpose and listed in the PR body: (a) `start` takes `--unit {contract}/{unit}`, `--task`, `--operator` and `--root` (default `.`, like every `taskcontract` command). `--task` is one of the seven ids in `taskcontract/data/tasks.yaml` (one source, the design's Sources); `--operator` is one of `qa`, `qa-verifier`, `developer`, `dev-verifier`, `receipts`, `orchestrator`, printed as the design's run draws them: QA, QA verifier, Developer, Dev verifier, receipts, Orchestrator. Any other value is argparse's usage error, exit 2. (b) `start` checks in this order, and each refusal writes nothing, goes to stderr and exits 1: the declaration (SC2.3); the git repository (`Task {task} did not start: no git repository at {root}.`, Claude's words, in node's form); a running task (the design's `Task {task} did not start: task {running} is running.`); `progress start` for `{unit}/{task}`, whose refusal lines print verbatim (the G1 line among them). Only then does it write the task file and print `Task {task}: {Operator}, round 1` to stdout, exit 0. The two writes-nothing refusals come before `progress start` because that call writes a record. (c) "No `test.command`" means any value that is not a non-empty list of non-empty strings: no config, a config that does not parse (as `g1.read_config` reads it), no `test:` block, no `command`, an empty list, a string. The message is the requirements' verbatim line; it names the declaration as "test command", which answers the sketch's "names the missing `test.command`". `file` and `build` read as empty when absent; what they run is e2's. (d) The task file is `sdlc-task.json` in the folder `git rev-parse --absolute-git-dir` names: `.git/` in a clone, the worktree's own folder in a linked worktree. Its text is the design's, `{"task":"green","operator":"developer","round":1}`. A file that is not a JSON object naming a task is no running task, and `start` replaces it. (e) The round is always 1 here: e5 adds the rounds file and the count. (f) `task.py` puts its own plugin root (two folders up) first on `sys.path`, so it reads the `taskcontract` that ships beside it, in the kit and in a consumer's plugin copy. (g) The kit's own blocks: `command: [python, -P, -m, pytest, tests, -q, -n, auto]` (CONTRIBUTING's suite command), `file: [python, -P, -m, pytest, "{file}", -q]`, no `build`, and `wall: functional: [tests/]`, as the design says. (h) The reader is `taskcontract/declaration.py`: `read_test(root)` returns the three lists or None; `wall:` is declared and documented here and read by e3's hook. (i) One session, no split at the test list (w3: 126K, 70K and 101K agent tokens).
7. What could go wrong, already ruled. The drafter fixes a detail the design leaves open: Claude checks each against the design before approval and lists it in the PR body. A test that imports `taskcontract.declaration` at module level is a collection error, not a red: the drafter imports it inside each test. A fixture repo needs `git init` and a ready contract for `progress start`: `tests/test_g1_start.py` builds one. The task file lands in the real repo's `.git/`: every test passes `--root` to its own scratch repo. Two-Key fails a round: one narrow fix round, tests first; after a third failure Claude stops.

10. Words. Declaration: the `test:` and `wall:` blocks of `.sdlc/config.yaml`. Test command: `test.command`, the argv the team runs for the whole suite. Wall: the paths each side never reads (functional tests from the Developer; unit tests and implementation bodies from QA).
